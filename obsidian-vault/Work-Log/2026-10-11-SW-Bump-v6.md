# 2026-10-11 (part 6) — SW cache bump v5→v6 so installed PWAs get the new Insights features

Back to [[Work-Log]] · [[Home]]

**Domain(s):** PWA / Service worker
**Branch:** `claude/vendora-pos-v3-KPnI0`

## Context
Owner: *"those are not in PWA."* The recent Insights work (map-zoom radius, "Who lives here") is frontend-only, and
frontend-only deploys don't change `public/sw.js`, so the installed PWA's service worker never flags an update — it keeps
serving the old cached bundle (hashed JS is stale-while-revalidate). This is the known F10 behaviour: a new build sits
"waiting" and the app shows a **Refresh** toast only when the SW file itself changes.

## Change
- `public/sw.js`: `CACHE_VERSION` `vendora-v5` → `vendora-v6` (the file's own instruction: bump it whenever a release should
  reach installed apps). This makes the browser see a **new** service worker on next open → it installs + waits → the
  existing client prompt (`src/pwa.js` `promptRefresh`) shows the **Refresh** toast → tapping it posts `SKIP_WAITING` and
  reloads into the new bundle (ignored → applies on next full reopen anyway). No logic change; just forces propagation.

## Important — two layers to "it's not in the PWA"
1. **Deployed?** The new bundle must be built by Vercel for the URL the PWA points at (the production branch / the branch
   the installed app was added from). A push to the feature branch only helps if that's what the PWA's URL serves.
2. **Picked up by the installed app?** This SW bump + Refresh prompt (or fully closing & reopening the PWA) handles it.
3. The **data** parts ("Who lives here" breakdowns, radius numbers) ALSO need the **Render backend redeploy** + test-unlock
   + centroids — those are server-side and independent of the PWA bundle.

## Verification
- `npm run build` green; `dist/sw.js` contains `vendora-v6`. Runtime SW behaviour not unit-tested (unchanged mechanism).
