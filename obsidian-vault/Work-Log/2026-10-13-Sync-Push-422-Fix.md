## Root cause
The frontend's `STORE_NAMES` (storage.js) had grown to 33 stores, but the backend's `ALLOWED` set
(pwaSyncService.js) still listed only 22. The push loop did `if (!ALLOWED.has(name)) throw AppError.validation(...)`
(**422**) — so the FIRST change for a store the server didn't know (e.g. `business_profile_v1` written during
onboarding, or any compliance-tool store) **rejected the entire push**, wedging ALL cross-device sync. The 3ms
422 in the Render log is that fast validation reject.

Missing stores: `business_profile_v1`, `temperature_log_v1`, `refusals_log_v1`, `refusals_signoff_v1`,
`scale_checks_v1`, `food_registration_v1`, `licence_log_v1`, `trading_permits_v1`, `animal_licence_v1`,
`recall_log_v1` (10) — plus they're non-financial, so all roles may sync them (no gating change needed).

## Changes
- `backend/src/services/pwaSyncService.js` — added the 10 missing stores to `ALLOWED`. **Hardened the push**:
  an unknown store or an oversized value is now **rejected per-item** (`rejected: [{name, reason:'unknown'|'too_large'}]`)
  instead of throwing a 422 that wedges the whole batch — so a client ahead of the server degrades gracefully
  (known stores still sync). `changes`-not-array and `>40 changes` stay hard 422 (malformed request / abuse bound).
- `backend/src/__tests__/pwaSync.integration.test.js` — updated the two "rejected (422)" cases to the new
  per-item contract; added a "business-profile + compliance stores sync" case (DB-gated).
- `frontend/src/lib/storage.js` — comment: keep `STORE_NAMES` in lockstep with the backend `ALLOWED` set.
- `public/sw.js` — v35 → v36.
